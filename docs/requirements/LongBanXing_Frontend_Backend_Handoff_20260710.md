## 0. 给后端开发对话的直接执行指令

请先审查现有代码，再按本文进行接口和运行时设计，不要直接在旧坐标脚本、旧马贼模式或旧副本步骤模型上改名堆字段。

本文的最高优先级原则是：

> 前端只负责收集用户意图、管理角色级配置、发出高层命令并展示后端状态；识别、判定、计时、寻路、目标选择、技能释放和实际执行全部由后端负责。

本文中的“前端状态”只能来自后端结构化快照。前端可以显示剩余时间、当前数量、当前阶段和识别结果，但不得自行据此决定“可以执行”、推进业务状态机或补发输入。用于视觉平滑的本地倒计时也不具有业务权威，最终是否可执行必须由后端再次判定。

本文使用以下规范词：

- **必须 / 不得**：强制契约，验收失败即不能开放功能。
- **应**：默认实现要求，若不采用必须在评审记录替代方案。
- **可以**：非强制实现建议。

任何与本文冲突的旧页面、旧 Mock 数据、旧坐标配置和旧说明文字，均以本文为准。

后端交付前必须提供：

1. 角色会话级配置和运行上下文。
2. 各模块的高层配置契约、命令契约和只读运行快照。
3. 可回放的状态机测试，不以“页面能点”作为完成标准。
4. 明确标注尚未真实闭环的能力，不能让前端显示可用开关。
5. 稳定错误码、命令幂等语义、配置修订冲突处理和会话隔离证据。

## 1. 产品结论

这次不是继续优化传统脚本配置器，而是把产品收敛为 AI Agent 控制台。

玩家需要看到的只有：

- 当前角色。
- 当前模式。
- 必要的开关、顺序、名单和动作选择。
- 当前运行状态、冷却状态、数量和异常。

玩家不应该看到：

- X/Y 坐标。
- OCR 或模型识别区域。
- 扫描间隔、点击延迟、重试次数、公共冷却等毫秒参数。
- 输入通道、窗口消息、客户端点击等执行方式。
- 识别阈值、模板路径、样本路径和置信度参数。
- “AI 将会……”“前端只负责……”等开发说明。
- 尚未接入后端却可以操作的假开关。
- 大段功能介绍、原理解释和重复提示。

运行状态不是“注释性信息”，应保留，例如：

- 运行中
- 已暂停
- 内挂监控中
- 世界频道冷却 02:18
- 当前击杀 37 / 100
- 正在前往点位 3
- 未就绪
- 执行失败

## 2. 前后端职责边界

### 2.1 前端负责

- 展示角色、门派和模块状态。
- 修改玩家可理解的声明式配置。
- 喊话条目的新增、删除、启停和排序交互。
- 巡逻点、白名单等后端对象的列表展示和管理操作。
- 发出以下高层命令：
  - 启动
  - 暂停
  - 停止
  - 记录当前点位
  - 截图添加当前目标
  - 删除条目
  - 调整顺序
- 展示后端推送的运行快照。
- 展示后端识别出的角色、门派、地图、目标和阶段；不得在 ViewModel 内重新识别或推断。
- 根据 capability 决定入口是否可用；不得用硬编码“已就绪”替代后端能力状态。

### 2.2 后端负责

- 窗口绑定和角色身份识别。
- 角色名、门派、等级、地图、位置、目标和队伍区域识别。
- 所有状态机、冷却、轮询、导航、抢目标、攻击、治疗和恢复。
- 世界频道三分钟冷却。
- 内置挂机运行状态监控和恢复。
- 巡逻点真实坐标、地图锚点和路线规划。
- 杀怪数量的数据源选择、去重和阈值动作。
- BOSS 截图识别、白名单硬门禁和爆发技能。
- 副本识别、阶段推进、目标优先级和禁止攻击规则。
- 背包、材料、活动 NPC、任务类型、题目与答案的识别和执行。
- 技术参数、模型参数和执行参数的内部存储。

### 2.3 强制会话隔离

所有配置、命令、冷却和状态必须绑定：

- `RoleSessionId`
- `CharacterProfileId`
- `WindowHandle`

`WindowHandle` 是后端会话上下文，不是角色配置主键，也不是玩家字段。前端动作应只发送 `RoleSessionId / CharacterProfileId`；后端在执行前解析并复核当前窗口，避免前端携带已失效句柄。

不能继续使用“一份全局当前窗口 + 一套单例控制器”覆盖多个角色。

每个角色会话必须独立拥有：

- 配置修订号。
- 运行状态机。
- 取消令牌。
- 喊话队列游标。
- 频道冷却。
- 巡逻进度。
- 杀怪计数。
- BOSS / 副本当前阶段。

### 2.4 多角色会话并发后端边界

#### 2.4.1 当前能力事实

截至 2026-07-11，当前程序只具备：

- 扫描并发现多个 `Game.exe` 窗口；扫描只刷新候选，不自动绑定，必须由玩家明确选择。
- 为发现的窗口截取头像区域，并在左侧显示多条窗口会话。
- 在没有任务占用执行器时，选择其中一个窗口作为全局当前窗口。
- 为当前窗口加载一套方案，并使用主界面唯一一组启动、暂停、停止命令。

当前程序**不具备 1–4 个角色窗口独立并行执行能力**，不能把“发现了多个窗口”表述为“支持多开独立挂机”。依据如下：

仓库已出现 `IRoleSessionManager / RoleSessionManager`、命令修订号和会话测试工具的 P0 骨架，但主界面尚未使用该管理器，配置、输入、控制器和 `AutomationRegistry` 仍是全局单例。该骨架只能算会话契约起点，不能作为并发完成证据。

| 当前实现 | 实际含义 |
|---|---|
| `IWindowBindingService.Current` 只有一个值 | 同一时刻只有一个全局当前窗口 |
| 切换角色会调用 `BindByHandle`，随后 `AutomationRegistry.AttachAll` | 切换会话是在覆盖全局控制目标，不是在切换独立运行上下文 |
| 配置服务、输入服务、控制器和 `AutomationRegistry` 均为单例 | 不同窗口会共享配置对象、运行字段、冷却和控制器目标 |
| 控制器只有一个可变 `Target` | 后一次绑定会覆盖前一次绑定 |
| 有控制器运行或暂停时禁止切换会话 | 这是当前单执行上下文的必要保护，不是并发能力 |
| 停止命令会遍历并停止全局控制器 | 不能做到“只停止角色 A，不影响角色 B” |
| 窗口方案映射使用“进程路径 + 规范化窗口标题” | 同路径、同标题的多个客户端可能映射到同一方案，不能代表真实角色身份 |

在以下后端验收全部通过前，前端和产品文案不得出现：

- “支持 1–4 窗口独立并行”。
- “每个角色可独立启动、暂停、停止”。
- “全部启动”以及任何暗示跨角色并行的批量启动按钮。
- “已自动识别角色并准确加载历史方案”。
- 多张角色卡同时显示为真实运行中。

当前前端可以继续保留多窗口发现、头像截图、窗口列表、当前窗口选择和只读状态展示，但启动命令必须明确只作用于当前绑定窗口与当前模式，并在任务运行时禁止切换窗口。现有“停止全部”是对全局单例控制器的安全急停，不代表已经具备跨角色批量控制；在会话隔离完成前不得把它拆成角色卡片上的独立停止。

#### 2.4.2 BOSS 与副本当前前端状态

当前 BOSS 和副本已经从旧马贼、旧坐标步骤页面中隔离，但这只证明正式前端不会误启动旧逻辑，不代表专项模式后端已经完成。

**BOSS 模式当前状态页：**

- 已有独立的极简状态页。
- 总开关存在但保持禁用。
- 状态固定显示“未就绪”。
- 白名单数量显示“—”，“管理白名单”保持禁用。
- 不进入可运行模式列表，不连接旧 `HorseBanditModeController`。
- 只有后端提供真实能力状态、结构化白名单、截图识别结果、极速控制器和运行快照后，前端才允许启用开关与白名单入口。

**副本模式当前状态页：**

- 已有独立只读状态页。
- 状态固定显示“未就绪”。
- “当前副本”和“当前阶段”均显示“—”，避免伪装成正在识别。
- 不显示副本下拉框、怪物名单、坐标或步骤编辑器。
- 不进入可运行模式列表，不连接旧 `DungeonController` 的坐标和热键步骤。
- 只有后端提供副本识别、版本化规则库、阶段推进、禁止目标门禁和结构化运行快照后，前端才允许启动。

BOSS 或副本页面上的静态“未就绪”文字不是运行状态证据。正式接入后，状态必须来自带 `RoleSessionId` 的后端能力快照；前端不得自行把开关变化解释为已启动。

#### 2.4.3 后端交付顺序

后端必须按以下顺序交付，不能先给前端增加四套按钮，再补运行隔离：

**P0：SessionManager 与窗口上下文**

1. 拆分全局窗口发现与会话执行上下文。
2. 完成现有 `RoleSessionId`、`RoleSessionSnapshot` 和 `IRoleSessionManager` 骨架与主应用、控制器作用域的真实集成。
3. `IRoleSessionManager` 为每个已接管窗口创建并持有独立服务作用域，限制为最多 4 个有效角色会话。
4. 所有启动、暂停、停止、配置和状态接口都必须显式携带 `RoleSessionId`。
5. 窗口重连只能替换所属会话的 `WindowHandle`，不能改写其他会话目标。

**P1：每会话配置与控制器**

1. 每个会话独立拥有配置快照、当前方案、修订号和自动保存队列。
2. 每个会话独立创建 `AutomationRegistry`、全部控制器、状态机、取消令牌和运行时服务。
3. 控制器目标在会话作用域内固定，禁止继续用全局 `AttachAll` 在角色间覆盖 `Target`。
4. 停止角色 A 只能取消 A 的任务；B、C、D 的控制器、配置和状态必须保持不变。
5. 底层配置文件仓库可以共享，但读取必须返回独立快照；保存必须使用原子写入和 `ExpectedRevision` 防止覆盖。

**P2：Input 隔离与前台仲裁**

1. 输入公共冷却至少按 `RoleSessionId / WindowHandle + ActionChannel` 隔离。
2. 输入方式、手动操作保护和暂停窗口不得继续使用一套全局可变字段。
3. `PostMessage` 可以按窗口并发；需要激活前台的 `SendInput` 必须经过全局仲裁器串行执行，避免角色间抢前台。
4. 每条输入结果必须回传所属 `RoleSessionId`，不能只写无会话归属的全局状态。

**P3：角色身份识别与方案映射**

1. 后端在绑定窗口后识别角色名、门派、等级及可用的区服身份。
2. 建立稳定的 `CharacterProfileId`，角色方案映射不能继续只依赖进程路径和窗口标题。
3. 只有精确匹配才能自动加载；低置信度、重名或证据冲突时返回 `NeedsConfirmation`，由玩家确认。
4. 确认后的角色身份、窗口会话和方案映射必须分开持久化，窗口句柄或进程重启不应丢失角色方案。

**P4：BOSS 与副本专项后端**

1. 先交付 BOSS / 副本能力探测和按会话结构化快照，替换前端静态“未就绪”。
2. BOSS 依次交付结构化白名单、截图候选、玩家确认、最终攻击硬门禁、极速选怪和爆发策略。
3. 副本依次交付副本识别、规则库版本、阶段事件、优先级、禁止目标和安全停止。
4. 专项控制器必须创建在角色会话作用域中，不得再次引入全局单例控制器。

**P5：并发验收与能力开放**

只有以下证据全部存在，前端才可以开放每张角色卡的独立启停，并宣称支持 1–4 窗口：

- 1、2、3、4 个会话分别通过创建、启动、暂停、恢复、停止和销毁测试。
- 四个独立测试窗口同时运行时，停止 A 不影响 B、C、D。
- A 修改或自动保存方案，不改变 B、C、D 的内存配置和磁盘修订。
- 同路径、同标题窗口可以通过确认后的角色身份绑定不同方案。
- 输入冷却、喊话频道冷却、巡逻进度、杀怪计数、返点状态和 BOSS / 副本阶段均不串会话。
- 角色 A 重连后只更新 A 的窗口上下文。
- 前端收到的每条命令结果、运行快照和日志都能按 `RoleSessionId` 归属。
- 完成四个真实游戏窗口的并行冒烟测试，并保留可回放日志、截图和资源占用记录。

## 3. 正式前端信息架构

### 3.1 角色设置首屏

角色设置打开后，第一屏就是“通用配置”，与门派选择属于同一个角色配置域；不得先出现概览仪表盘、纵向模式菜单或“高级设置”技术面板。

首屏只保留：

- 门派。
- 选怪 / 切换目标快捷键。
- 内置挂机快捷键。
- 玩家操作保护。
- 角色和宠物恢复配置。

门派由后端在绑定窗口后自动识别；手动选择只作为识别未就绪、低置信度或身份冲突时的兜底确认，不得由前端根据窗口标题猜测。

玩家操作保护只响应玩家真实鼠标按键，不响应键盘输入、鼠标移动或程序自身注入输入。前端只配置启用状态和暂停时长；点击归属、注入标记、目标窗口判定以及恢复时机由后端负责。

恢复配置包括：

- 角色回血。
- 角色回蓝。
- 宠物回血。
- 宠物口粮。
- 血祭回蓝。用户口述过“血迹”，正式名称需以游戏内文本确认。
- 共生回血。

宠物口粮、血祭回蓝、共生回血属于角色通用配置，不属于“高级设置”。

这些恢复项不使用滑杆，只使用开关、快捷键和必要的数字输入。数字是玩家声明的恢复策略，不是前端识别或触发判断：

```text
恢复项          开关       快捷键       触发值
宠物口粮        [开]       [F8]         [50] %
血祭回蓝        [开]       [F9]         [70] %
共生回血        [开]       [F10]        [70] %
```

前端只保存玩家选择；当前血量、是否需要恢复、技能是否可用以及何时执行全部由后端判定。后端若能完全托管某一触发值，应通过 capability 告知前端隐藏该输入，不得保留无效字段。

禁止在正式角色设置里恢复以下内容：

- 输入通道。
- 公共冷却。
- 点击坐标。
- 宠物技能点击位置。
- OCR 区域。
- 技能冷却模板采样。
- 测试、标定和识别阈值。
- 自动登录步骤和坐标动作。

这些内容如确需调试，只能进入开发者工具，并且正式版本默认不可见。

### 3.2 挂机中心

挂机中心保留：

- 挂机打怪
- BOSS 模式
- 副本模式
- 自动清包
- 材料加工

五项均按本文契约执行；后端未闭环的项只显示真实“未就绪”，不得复用旧页面制造可执行假象。

### 3.3 生活模块

喊话归入生活模块，但配置仍绑定当前角色，不做全局共享。

### 3.4 其他一级模块

正式一级 Tab 固定为：

1. 角色设置
2. 挂机
3. 活动
4. 生活
5. 任务
6. 答题

活动只保留自动反贼、自动宵小、自动和尚；生活只保留挖图、采矿、采药、跑商和喊话；任务只保留任务选择、任务类型策略和拖拽顺序；答题只保留开关、剩余次数或服务状态及当前答题状态。详细前后端边界见第 17 节。

## 4. 前端改造：喊话

### 4.1 页面目标

当前“一个多行文本框，每行一条”的方案废弃。

改为多个独立的长条喊话项：

```text
喊话                                          [总开关]

≡  喊话 1   [世界频道 ▼]   [请输入喊话内容................]   [开]   [删除]
≡  喊话 2   [帮派频道 ▼]   [请输入喊话内容................]   [关]   [删除]
≡  喊话 3   [队伍频道 ▼]   [请输入喊话内容................]   [开]   [删除]

[ + 新增喊话 ]
```

### 4.2 每条喊话必须支持

- 稳定唯一 ID。
- 自动编号为“喊话 1、喊话 2、喊话 3……”。
- 独立内容。
- 独立频道。
- 独立启用开关。
- 删除。
- 拖拽排序。
- 跟随当前角色自动保存。
- 运行时简短状态，例如“等待”“发送中”“世界冷却 02:18”“失败”。

编号是显示顺序，不是数据主键。拖拽后编号随顺序更新，但 ID 不变。

### 4.3 频道列表

根据用户提供的游戏频道图，频道单选项为：

1. 附近频道
2. 世界频道
3. 同城频道
4. 帮派频道
5. 同盟频道
6. 门派频道
7. 队伍频道

一条喊话只对应一个频道，不做多选。

### 4.4 执行顺序

- 后端按当前排序循环执行所有已启用且内容非空的条目。
- 禁用条目不进入队列。
- 暂停后保留当前游标，恢复时不重复提交上一条。
- 删除或排序在运行时生效，但不能造成当前条重复发送。
- 停止后不再发送任何输入。

用户强调“按照顺序自动喊话”，因此第一版按绝对顺序执行：

- 如果轮到世界频道但仍在三分钟冷却中，队列等待该条可发送后再继续。
- 不越过该条发送后续内容。

如果后续产品决定“世界频道冷却时先发其他频道”，只能修改后端调度策略，前端不增加技术开关。

### 4.5 世界频道冷却

- 固定 180 秒。
- 不给玩家编辑冷却时长。
- 由后端按角色会话计时。
- 发送结果不确定时，保守视为已发送并开始冷却，避免重复发送。
- 暂停、恢复或程序重启不能绕过冷却。
- 前端只显示后端返回的“可发送”或剩余时间。

### 4.6 正式页面必须删除

- “归入生活模块，配置跟随当前角色……”说明句。
- “开启后按顺序……”说明句。
- “每行一条内容”说明句。
- 多句循环开关；队列默认循环。
- 打开聊天快捷键。
- 发送确认快捷键。
- 发送间隔、输入延迟和确认延迟。
- 坐标、频道点击位置和重试参数。

## 5. 后端同步：喊话队列

### 5.1 配置与状态契约

```csharp
public enum ShoutChannel
{
    Nearby,
    World,
    SameCity,
    Guild,
    Alliance,
    School,
    Team
}

public sealed class ShoutQueueConfig
{
    public bool Enabled { get; set; }
    public List<ShoutQueueItem> Items { get; set; } = [];
}

public sealed class ShoutQueueItem
{
    public string Id { get; init; } = "";
    public int Order { get; set; }
    public bool Enabled { get; set; }
    public ShoutChannel Channel { get; set; }
    public string Text { get; set; } = "";
}

public sealed record ShoutItemRuntimeSnapshot(
    string ItemId,
    string State,
    int? RemainingCooldownSeconds,
    DateTimeOffset? CooldownUntil,
    string? ErrorCode);
```

配置更新使用公共 `ExpectedRevision` 契约。`Order` 必须归一化为连续顺序；`Id` 由后端或共享领域服务生成并保持稳定，前端显示编号不得写回为主键。

### 5.2 后端状态机

```text
Idle
→ ValidateQueue
→ SelectNextEnabledItem
→ CheckChannelCooldown
→ waiting_cooldown / SelectChannel
→ OpenChat
→ InputText
→ Submit
→ VerifyOrConservativeCommit
→ AdvanceQueue
→ SelectNextEnabledItem
```

`waiting_cooldown` 是严格队列的阻塞状态：当前世界频道条目冷却结束前，游标不得前移，也不得发送后续条目；倒计时结束后继续发送当前条目。若未来产品需要“跳过冷却项”，必须新增显式调度策略和独立验收，当前版本不得默认跳过。

### 5.3 后端验收

- 支持任意数量条目的增删、启停、排序和持久化。
- 七种频道均由后端选择，不依赖前端坐标。
- 同一角色两次世界频道提交间隔不少于 180 秒。
- 两个角色窗口的队列、游标和冷却互不干扰。
- 重排后不重复当前已发送条目。
- 空内容不发送，并返回简短校验状态。
- 世界频道最后一次保守提交时间必须持久化；暂停、进程重启和会话重连均不能清除 180 秒冷却。
- 轮到仍在冷却的世界频道条目时必须原地等待，不能越过它发送后续条目。
- 频道路由、聊天焦点或提交确认能力不可用时返回 `CHANNEL_ROUTER_NOT_READY` 或 `CHAT_SUBMIT_UNCERTAIN`，并保证不会无保护地继续输入。

## 7. 后端同步：内置挂机监控

### 7.1 行为定义

- 内置挂机固定点工作，不使用巡逻。
- 近战角色在游戏内挂下可能表现为远程攻击，这是游戏内挂行为，不需要前端配置。
- 某些人工或游戏操作会使内挂停止。
- 选择内置挂机后，后端自动启动看门狗，不再给玩家单独的“监控内挂”开关。
- 通用配置中的内置挂机快捷键只作为后端恢复动作输入。

### 7.2 必须避免盲按

内挂快捷键可能是 Toggle。后端在状态为 `Unknown` 时禁止直接按键，否则可能把正在运行的内挂关闭。

建议状态机：

```text
Idle
→ ObserveBuiltInState
→ Running
→ SuspectedStopped
→ DebounceAndRecheck
→ ConfirmedStopped
→ TriggerConfiguredHotkeyOnce
→ VerifyRestarted
→ Running / RecoveryFailed
```

要求：

- 连续多帧确认停止后才恢复。
- 一次触发后等待视觉确认。
- 同一故障周期不能连续狂按。
- 达到后端重试上限后熔断并上报“恢复失败”。
- 前端只显示“监控中 / 已恢复 / 恢复失败”。

### 7.3 当前代码事实

现有内挂服务只在启动或模式切换时触发一次快捷键，没有持续监控；现有 `InternalPluginCombatBackend.Read` 也没有返回真实内挂开关状态。因此本项是后端新增能力，不是前端补一个开关即可完成。

## 8. 后端同步：按键打怪与定点巡逻

### 8.1 点位管理

玩家只执行“记录当前点位”。

前端展示：

```text
≡ 点位 1 · 已记录     [删除]
≡ 点位 2 · 已记录     [删除]
≡ 点位 3 · 已记录     [删除]

[ + 记录当前点位 ]
```

前端不展示 X/Y，也不让玩家手工输入位置。

后端负责：

- 识别当前地图和真实位置。
- 保存点位锚点。
- 删除和重排。
- 到达判断。
- 区域无怪判断。
- 规划到下一点的路线。
- 最后一点结束后循环第一点。

不要复用“返点”对象冒充巡逻点。巡逻点和返点语义不同，应使用独立契约。

### 8.2 巡逻状态机

```text
ScanCurrentArea
→ FoundMonster → Engage
→ ConfirmKillOrTargetInvalid
→ ScanCurrentArea
→ ConfirmAreaEmpty
→ NavigateToNextPoint
→ DetectMonsterDuringNavigation
   ├─ Found → SuspendNavigation → Engage → ResumeNavigation
   └─ NotFound → ContinueNavigation
→ Arrive
→ ScanCurrentArea
→ Loop
```

“区域无怪”不能用一次识别结果决定。后端需要结合连续无合法目标、不在战斗、目标未处于短暂丢失等条件做稳定判定，但这些条件和时间不出现在前端。

### 8.3 自动切怪

- 按键打怪强制开启自动切怪。
- 旧角色方案即使保存了 `AutoAcquireWhenNoTarget=false`，迁移后也必须按新规则视为 `true`。
- 不能仅隐藏旧开关，否则旧配置仍会导致实际不切怪。

## 9. 后端同步：攻击玩家

### 9.1 产品规则

- 仅按键打怪显示和生效。
- 默认关闭。
- 内置挂机不显示、不执行。
- 开启后仍需后端确认目标确实是玩家。
- NPC、宠物、队友和识别不确定目标不得因为该开关被误攻。

### 9.2 技术门禁

攻击输入前必须再次执行安全判断：

```text
目标识别
→ 玩家 / 怪物 / NPC / 宠物分类
→ 队伍及保护关系判断
→ 当前模式和用户策略判断
→ Allowed 才能发送攻击
```

现有配置以 `Targeting.BlockPlayerTargets=true` 作为安全默认值，前端“攻击玩家”使用反向绑定。该字段只能表达玩家策略，不能代替目标分类；后端仍必须在最终攻击输入前执行玩家、队友和不确定目标门禁，并确保旧配置迁移不会意外放宽保护。

### 9.3 尚需产品确认

“攻击玩家”第一版是否表示任意非队友玩家，还是只攻击红名 / 敌对玩家，后端实现前必须确认。默认建议：开启后仍强制排除队友，其他关系由明确策略处理。

## 10. 后端同步：峨眉加血与门派识别

### 10.1 前端规则

- 仅门派为峨眉时显示。

```text
MonitorSelfAndParty

→ RestoreCombatTarget
```

后期可以实现，而且应由后端完成。

```csharp
public sealed record RoleIdentitySnapshot(
    string CharacterName,
    School? School,
    int? Level,
    string Status,
    int ConfidencePercent,
    string Source);
```

规则：

- 高置信度时自动载入角色门派和配置。
- 低置信度时返回“待确认”，由玩家选择。
- 玩家手动确认拥有最高优先级，后续自动识别不得静默覆盖。


### 12.2 后端数据源

建议抽象 `IKillCounterProvider`，按稳定性选择：

1. 版本匹配且已验证稳定的内存数据。
2. 游戏面板视觉 / 图色 / OCR。
3. Agent 自有确认计数器。

前端不知道也不选择来源。

Agent 自有计数不能把“目标丢失”直接当成死亡，至少需要：

- 合法怪物目标。
- 确认进入战斗。
- 可靠死亡证据或生命状态边沿。
- 同一目标实例去重。

达到阈值后的动作必须幂等，同一轮只能触发一次。

### 12.3 默认口径与待确认项

建议第一版：

- 每次新启动挂机会话时清零。
- 暂停 / 恢复不清零。
- 达到 `N` 只时触发，即 `count >= N`。

仍需确认：

- 回城后是否清零并继续。
- 程序重启是否恢复本轮计数。
- “下线”具体指退到角色选择、断开游戏连接还是关闭客户端。

## 16. 后端同步：副本规则引擎

### 16.1 架构要求

现有副本模型是热键、坐标和点击步骤列表，不适合新需求。

需要新增数据驱动规则库，而不是继续扩展旧 `DungeonScriptStep`：

```csharp
public sealed class DungeonDefinition
{
    public string Id { get; set; } = "";
    public string DisplayName { get; set; } = "";
    public List<MapMatcher> MapMatchers { get; set; } = [];
    public List<EncounterRule> Encounters { get; set; } = [];
    public string Revision { get; set; } = "";
}

public sealed class EncounterRule
{
    public string Id { get; set; } = "";
    public string ActivateCondition { get; set; } = "";
    public List<TargetRule> Priorities { get; set; } = [];
    public List<TargetRule> HardExclusions { get; set; } = [];
    public string CompleteCondition { get; set; } = "";
    public string NextEncounterId { get; set; } = "";
}
```

规则库必须：

- 独立版本号。
- 支持更新和回滚。
- 通过地图和感知结果自动选择。
- 将禁止攻击规则置于最高优先级。
- 未匹配明确副本时停止，不回退到普通乱打。

### 16.2 燕子坞初始规则

燕子坞必须分成“出现条件”和“攻击优先级”两个维度，不能把两者合并成一条四连顺序。

当前已明确的硬门禁：

1. 岳老三必须先处理；岳老三死亡前不得推进后续阶段。
2. 岳老三死亡后，云中鹤和叶二娘才进入可处理范围。
3. 云中鹤死亡后，段延庆才具备出现条件。

当前已明确的攻击优先级为：

```text
岳老三 → 云中鹤 → 叶二娘
```

段延庆和叶二娘的最终攻击先后当前待后端数据库与实测样本确认。“段延庆可出现”不等于“立即越过叶二娘攻击”。规则必须写入版本化数据库；样本结论只调整后端规则数据，不得把顺序选项暴露给玩家或在前端写死。

### 16.3 缥缈峰桑土公规则

- 桑土公会召唤僵尸类小怪。
- 该僵尸必须进入硬排除名单，任何情况下不得选择或攻击。
- 当前交接使用“碧鳞僵尸”作为产品名称；后端录入前仍需用游戏内样本核对字形。
- 如果样本证明存在 OCR 变体，可维护受控别名，但不能放宽为不受控模糊匹配。

### 16.4 副本状态机

```text
IdentifyDungeon
→ LoadVersionedDefinition
→ ResolveEncounter
→ WaitForActivationCondition
→ ScanTargets
→ ApplyHardExclusions
→ ApplyPriority
→ AcquireAndFight
→ ConfirmDeathOrStageCondition
→ AdvanceEncounter
→ CompleteDungeon
```

### 16.5 验收

- 玩家无需选择副本和配置步骤。
- 地图识别后自动加载正确规则版本。
- 燕子坞每个出现条件和优先级有回放测试。
- 桑土公阶段无论僵尸和 BOSS 是否重叠，都不能向僵尸发送攻击。
- 不确定当前副本或规则版本时停止执行并上报状态。

## 17. 扩展模块前后端契约

本节补齐自动清包、材料加工、活动、生活、任务和答题。共同规则是：前端只保存玩家可理解的高层选择并显示状态；后端能力未闭环时统一返回 `NotReady`，前端不得保留旧 Mock 表单或用本地开关模拟运行。

### 17.1 自动清包

前端只提供：

- 启用状态。
- 清包方式：月卡清包或回城清包。
- 回城地点：洛阳、苏州、大理、楼兰。
- 允许出售名单的增删和启停。
- 候选数量、当前阶段、成功或阻塞原因。

后端负责：

- 识别背包容量、物品名称、数量、绑定状态和月卡能力。
- 根据方式执行月卡入口，或识别地图并寻路到对应城市的安全 NPC。
- 只把明确匹配“允许出售名单”的物品加入候选；未知、识别不确定和规则冲突物品一律保护。
- 出售前再次校验候选快照、物品身份和配置修订号，避免背包变化后误售。
- 安全出售闭环未通过验收前只生成候选，不执行出售。

前端不得展示背包格坐标、NPC 坐标、模板阈值、价格规则和点击步骤。建议阶段为 `Inspecting / CandidateReady / Returning / Selling / Completed / Blocked`。

### 17.2 材料加工

前端只提供：

- 启用状态。
- 加工周期。
- 上次执行、下次计划、当前状态和异常。

后端负责背包识别、材料分类、加工入口识别、是否可以加工、执行全部可加工材料以及结果验证。玩家不选择配方、格子、点击顺序或识别参数。周期由后端权威计时；前端显示计划时间但不自行触发加工。

### 17.3 活动

活动只包含：

1. 自动反贼
2. 自动宵小
3. 自动和尚

每项前端只提供启用状态和找点方式：

- `AutoFind`：后端根据当前角色门派、地图、刷新周期和活动规则选择有效等待点。
- `ManualPosition`：玩家自行把角色带到等待位置，前端只发送“开始等待”高层命令，不记录或展示坐标。

刷新时间、地图和门派匹配、NPC 识别、周围玩家干扰处理、对话交互、进入活动和失败恢复全部由后端负责。页面只显示 `等待刷新 / 发现目标 / 交互中 / 已进入 / 未就绪 / 失败` 等短状态。

### 17.4 其他生活能力

生活模块除喊话外只保留：

- 挖图
- 采矿
- 采药
- 跑商

这些能力当前没有真实后端闭环时只显示极简“未就绪”状态页。不得恢复旧路线、坐标、步骤队列或假数据；未来每项都应有独立 feature key、状态机和运行快照，不能混入一个生活大循环。

### 17.5 任务中心

任务列表固定为：

1. 师门任务
2. 帮贡任务
3. 新鸳鸯蝴蝶梦
4. 百变脸谱
5. 一千零一个愿望

前端允许：

- 每项独立启用或停用。
- 拖拽执行顺序。
- 师门任务类型策略：打怪、送信、抓宝宝、买物品 / 药品。
- 发送一次“执行日常任务”高层命令并显示任务、阶段和结果。

关闭某个师门任务类型表示明确策略：后端识别到该类型后按游戏安全流程放弃任务。例如关闭“买物品 / 药品”，接到购买类任务后应自动放弃；前端不编辑放弃步骤。

后端负责门派、任务、任务类型、NPC、地图和物品识别，规划任务顺序并执行。取消旧步骤编辑器、动作队列和玩家自定义脚本。任务计划 DTO：

```csharp
public sealed record DailyTaskPlanDto(
    IReadOnlyList<DailyTaskItemDto> Items,
    SchoolTaskPolicyDto SchoolPolicy);

public sealed record DailyTaskItemDto(
    string TaskKey,
    int Order,
    bool Enabled);

public sealed record SchoolTaskPolicyDto(
    bool Fight,
    bool DeliverMessage,
    bool CapturePet,
    bool BuyItem);
```

`TaskKey` 使用稳定枚举或受控字符串；显示编号不是主键。后端必须返回当前任务、当前阶段、放弃原因和剩余队列，前端不得根据排序自行启动下一任务。

### 17.6 答题助手

答题是独立一级 Tab。前端只显示：

- 开启 / 关闭。
- 剩余次数或服务状态。
- 当前答题状态和一条可处理异常。

后端负责服务权益校验、题目识别、题库匹配、答案判定、提交和结果确认。剩余次数为后端权威数据，前端不得本地扣减。题库或执行器未接入时 capability 必须为 `NotReady`，开关保持不可用。

### 17.7 扩展模块开放门禁

| 模块 | 可开放配置入口的最低能力 | 可开放启动的最低能力 |
|---|---|---|
| 自动清包 | 名单持久化与候选预览 | 候选复核、出售验证和恢复链路全部就绪 |
| 材料加工 | 周期配置持久化 | 背包识别、加工执行和结果验证全部就绪 |
| 活动 | 活动配置持久化 | 对应活动识别、找点 / 等待和交互状态机就绪 |
| 挖图 / 采矿 / 采药 / 跑商 | 对应 feature capability 为 `Ready` | 对应独立状态机为 `Ready` |
| 任务 | 计划和类型策略持久化 | 任务识别、放弃策略和任务执行器就绪 |
| 答题 | 服务状态查询 | 权益、识题、判题、提交和结果确认就绪 |

## 18. 公共后端协议

### 18.1 Feature Key 与 capability

每项能力使用稳定 `FeatureKey`，至少包括：

```text
role.common
life.shout
hang.normal
hang.boss
hang.dungeon
hang.cleanup
hang.material
activity.rebel
activity.xiaoxiao
activity.monk
life.treasure-map
life.mining
life.herb
life.trade
task.daily
quiz.assistant
```

capability 与运行状态必须分开，避免把“已接入”误当成“正在运行”：

```csharp
public enum FeatureAvailability
{
    Unavailable,
    NotReady,
    Ready
}

public enum FeatureRunState
{
    Stopped,
    Starting,
    Running,
    Pausing,
    Paused,
    Stopping,
    Completed,
    Error
}

public sealed record FeatureCapabilitySnapshot(
    string RoleSessionId,
    string CharacterProfileId,
    string FeatureKey,
    FeatureAvailability Availability,
    bool CanConfigure,
    bool CanStart,
    string? BlockingReasonCode,
    string? BlockingSummary,
    long CapabilityRevision,
    DateTimeOffset UpdatedAt);
```

前端只有在 `Availability == Ready && CanStart` 时才能启用启动入口。`NotReady` 必须带稳定原因码；前端不得把本地配置完整、按钮打开或静态文案解释为 `Ready`。

### 18.2 角色通用配置与挂机配置 DTO

- `RecoveryKey` 受控为角色回血、角色回蓝、宠物回血、宠物口粮、血祭回蓝、共生回血；前端使用数字输入而非滑杆。

- `PatrolPointSummaryDto` 只给前端 ID、顺序、名称和状态；真实地图、位置和路线只保存在后端。
- `TriggerPercent` 是玩家恢复策略；实时血量识别、技能可用性和触发时机仍由后端负责。

| Feature | 前端可写配置 | 后端只读 / 内部数据 |

| `hang.boss` | 总开关、系统项启停、用户名单管理命令 | 截图、OCR 候选、别名、极速策略、最终白名单门禁 |
| `hang.dungeon` | 总开关 | 地图、副本、规则版本、阶段、目标优先级和硬排除 |
| `hang.cleanup` | 开关、方式、城市、允许出售名单 | 背包快照、候选、NPC、路线、出售复核 |
| `hang.material` | 开关、加工周期 | 材料识别、加工步骤、结果验证 |
| `activity.*` | 开关、找点方式 | 刷新时间、位置、NPC、地图、交互状态机 |
| `task.daily` | 任务开关、顺序、师门类型策略 | 任务识别、规划、放弃流程和执行阶段 |
| `quiz.assistant` | 开关 | 权益、剩余次数、题目、答案和提交结果 |

### 18.3 配置更新、命令与幂等

```csharp
public sealed record ConfigUpdate<T>(
    string CommandId,
    string RoleSessionId,
    string CharacterProfileId,
    string FeatureKey,
    long ExpectedRevision,
    T Config);

public sealed record FeatureCommand<T>(
    string CommandId,
    string RoleSessionId,
    string CharacterProfileId,
    string FeatureKey,
    long ExpectedRevision,
    string Action,
    T Payload);

public sealed record CommandResult(
    string CommandId,
    string RoleSessionId,
    string FeatureKey,
    bool Accepted,
    bool IsReplay,
    string ResultCode,
    string Summary,
    long CurrentRevision,
    long SnapshotSequence);
```

要求：

- 所有配置写入和动作命令都携带全局唯一 `CommandId`，同一命令重试必须返回第一次的等价结果，不能重复产生副作用。
- 配置写入携带 `ExpectedRevision`；冲突返回 `REVISION_CONFLICT` 和当前修订号，禁止后写静默覆盖。
- 启动、暂停、停止、记录点位、截图添加、名单确认、回城、下线、出售和放弃任务等动作必须幂等。
- 命令已受理但最终结果尚未产生时返回结构化 `Accepted`，后续结果通过快照关联 `CommandId`，不能让前端靠超时猜测后重发。
- 删除、排序和启停运行中对象时，后端在修订边界上原子应用，并保证当前喊话、巡逻点或任务不会重复执行。

### 18.4 运行快照

```csharp
public sealed record FeatureRuntimeSnapshot<TDetail>(
    string RoleSessionId,
    string CharacterProfileId,
    string FeatureKey,
    FeatureRunState RunState,
    string Phase,
    string Summary,
    string? BlockingReasonCode,
    string? LastErrorCode,
    string? LastCommandId,
    long ConfigRevision,
    long Sequence,
    TDetail Detail,
    DateTimeOffset UpdatedAt);
```

`Sequence` 在同一角色会话和 feature 内单调递增；前端必须丢弃倒序旧快照。各模块的 `Detail` 至少返回：

- 喊话：当前条目、频道、队列游标、剩余冷却、冷却截止时间。
- 内挂：当前观测状态、疑似停止、恢复中、恢复失败。
- 巡逻：点位摘要、当前顺序、导航 / 战斗状态。
- 峨眉：自身能力、队伍感知 capability、当前治疗状态。
- 返点：触发原因、方式、当前阶段、是否到达。
- 杀怪：当前数量、目标数量、数据源健康状态、阈值动作状态。
- BOSS：候选、白名单门禁结果、当前目标和战斗阶段。
- 副本：副本 ID、规则版本、当前阶段、当前优先目标、硬排除命中。
- 清包：背包状态、候选数量、复核状态和出售阶段。
- 材料：材料数量、当前阶段、上次和下次计划时间。
- 活动：活动 ID、找点方式、刷新 / 交互阶段。
- 任务：当前任务、任务类型、当前阶段、放弃原因和剩余队列。
- 答题：服务状态、剩余次数、当前阶段和提交结果。

前端不根据日志文本、开关值或最后一次按钮点击猜状态。识别结果也只能消费后端快照，不能在 ViewModel 内二次判定。

### 18.5 统一错误码

后端至少提供以下稳定错误码；`Summary` 是简短用户文案，不能代替错误码：

| 错误码 | 含义 |
|---|---|
| `SESSION_NOT_FOUND` | 角色会话不存在或已关闭 |
| `WINDOW_NOT_BOUND` | 会话没有有效游戏窗口 |
| `IDENTITY_NEEDS_CONFIRMATION` | 角色或门派识别需要玩家确认 |
| `FEATURE_NOT_READY` | 对应 capability 尚未就绪 |
| `FEATURE_NOT_APPLICABLE` | 当前模式或门派不适用 |
| `REVISION_CONFLICT` | 配置修订冲突 |
| `INVALID_CONFIG` | 高层配置不合法 |
| `CHANNEL_ROUTER_NOT_READY` | 喊话频道路由不可用 |
| `CHAT_SUBMIT_UNCERTAIN` | 喊话提交结果不确定，已按保守规则记冷却 |
| `COOLDOWN_ACTIVE` | 后端权威冷却尚未结束 |
| `NAVIGATION_NOT_READY` | 地图识别或自动寻路不可用 |
| `PARTY_VISION_NOT_READY` | 队伍区域识别不可用 |
| `TARGET_NOT_WHITELISTED` | BOSS 最终白名单门禁拒绝 |
| `MAP_UNRECOGNIZED` | 无法确认地图或副本 |
| `RULESET_UNAVAILABLE` | 对应规则版本不可用 |
| `SAFE_SELL_BLOCKED` | 清包安全复核未通过 |
| `SERVICE_QUOTA_UNAVAILABLE` | 答题服务或剩余次数不可用 |
| `CANCELLED` | 命令被安全取消 |
| `EXECUTION_FAILED` | 已执行但未达到可验证结果 |

### 18.6 会话隔离与生命周期

- 所有 capability、配置、命令、快照、冷却、游标、计数和日志显式携带 `RoleSessionId`。
- `CharacterProfileId` 绑定角色持久配置；`WindowHandle` 只属于当前运行窗口，重连不得生成另一份角色配置。
- 前端命令不直接指定原始 `WindowHandle`；后端按 `RoleSessionId` 解析并校验窗口所有权，窗口已替换时拒绝旧执行上下文。
- 同一有效窗口同一时刻只能属于一个角色会话；会话更换窗口时必须取消旧执行、清理旧命令缓存和模块快照后再发布 `Ready`。
- 已关闭的 `RoleSessionId` 不得复用；迟到命令和快照必须拒绝或丢弃。
- 最多 4 个活动会话。角色 A 的停止、重连、配置保存、喊话冷却或模块错误不得改变 B、C、D。
- 需要前台输入的动作经过全局仲裁器，但结果、冷却和异常仍归属原角色会话；仲裁器不得把全局串行误实现为全局状态共享。

### 18.7 日志与诊断

普通用户状态只提供短文本、当前动作和可处理异常。

前端必须执行失败关闭（fail-closed）的用户日志投影：只有 `Audience=User` 且已生成脱敏 `UserSummary` 的记录可以展示或导出。窗口句柄、PID、内部模块名、异常原文、路径、模型/引擎、坐标/ROI、密钥、内部配置键、原始识别文本、样本和置信分数均不得进入正式界面、辅助功能树、剪贴板或用户导出文件。

以下详细信息进入默认隐藏的开发诊断流，不进入正式卡片：

- 原始 OCR 文本和置信度。
- 坐标和识别区域。
- 模型版本。
- 输入通道。
- 重试次数和内部延迟。
- 状态机详细转换原因和堆栈。

日志条目必须带 `RoleSessionId / FeatureKey / CommandId（若有）/ Timestamp`，才能回放并区分多角色问题。

原始开发遥测必须默认关闭且不得进入 Release；崩溃反馈只提供无技术细节的反馈编号。正式运行记录固定为“时间 / 状态 / 事件”，复制和导出必须与当前可见脱敏集合一致。

### 21.2 后端行为验收

- [ ] 清包未知物和快照冲突时停止出售；材料加工不会重复执行同一调度周期。
- [ ] 活动、任务、答题在识别不确定或服务不可用时安全停止并返回稳定错误码。

### 21.3 契约与自动化检查

必须增加以下自动化测试：

1. capability 契约测试：`NotReady` 时所有启动命令返回 `FEATURE_NOT_READY`。
2. DTO 序列化测试：正式前端 DTO 不包含坐标、区域、输入通道、扫描 / 点击间隔、阈值和模型路径。
3. 幂等测试：相同 `CommandId` 并发、超时重试和重连重放均只产生一次副作用。
4. 修订测试：自动保存与手动动作并发时，旧 `ExpectedRevision` 必须冲突。
5. 快照顺序测试：前端收到较小 `Sequence` 时丢弃，不能回退状态。
6. 会话串扰测试：A 的冷却、计数、游标、阶段、错误和取消均不改变 B。
7. 回放测试：挂机、BOSS、副本、活动、清包、任务和答题覆盖正常、失败、取消和恢复。
8. 正式 UI 文本与绑定扫描：开发工具以外禁止出现下列技术字段或同义玩家输入。

```text
X / Y 坐标
点击位置
识别区
扫描间隔
输入通道
公共冷却
延迟 ms
重试次数
模板阈值
模型置信度
样本路径
标定
PID / 进程路径 / 分辨率
```

允许在正式 UI 显示后端返回的业务状态，例如“世界频道冷却 02:18”；禁止的是让玩家编辑公共冷却或看到内部计时参数。开发诊断界面不参与正式 UI 扫描，但必须通过显式开发模式开启且默认隐藏。

### 21.4 当前状态判定

当前已完成的通用配置、喊话队列结构、普通挂机页面清洗以及 BOSS / 副本极简状态页，只能标记为“前端结构已落地”。第 21.1 表中任何后端证据缺失的模块都不得标记为“业务完成”，也不得开放假开关。

## 22. 需要产品确认的最小问题集

这些问题不阻塞前端先做结构，但会影响后端最终行为：

1. 攻击玩家是允许攻击任意非队友玩家，还是只攻击红名 / 敌对玩家？
2. 自动返点由哪些事件触发？
3. 内挂、巡逻各自使用哪个返点锚点？
4. 土灵珠失败时是否自动降级为自动寻路？
5. 杀怪回城后是否清零并继续？
6. “下线”具体指退到角色选择、断开连接还是关闭客户端？
7. BOSS 爆发技能来自过渡期技能预设，还是后端门派爆发库？
8. 燕子坞中叶二娘与段延庆的最终优先级；出现条件已明确，攻击先后仍需实测。
9. 月卡清包不可用时，是直接阻塞还是在玩家已选城市时降级为回城清包？
10. 活动手动找点模式由玩家主动点击“开始等待”，还是识别到到位后自动进入等待？
11. 日常任务某项失败后是跳过继续、整队停止，还是按任务类别采用不同策略？
12. 正式技能名“血祭回蓝”需以游戏内样本最终核对。

在这些问题确认前：

- 前端不要增加额外技术选项。
- 后端不要把猜测写死在控制器。
- 可变规则进入版本化数据库或策略文件。

## 24. 最终完成定义

只有同时满足以下条件，才算本轮完成：

1. 玩家界面已经清洗为“模式、开关、名单、顺序、状态”。
2. 正式 UI 不再暴露坐标、识别和执行参数。
3. 前端没有承担冷却、计数、导航或战斗判断。
4. 所有可点击功能都存在真实后端命令和运行快照。
5. 所有配置和运行状态都按角色会话隔离。
6. 喊话、内挂、巡逻、杀怪、BOSS、副本、清包、材料、活动、任务和答题均有对应的正常、失败、取消及恢复验收证据。
7. capability、命令结果、错误码和快照满足第 18 节契约，前端不会依赖日志文本推断状态。
8. 1–4 个角色会话通过隔离验收，任何配置、冷却、计数、阶段和输入结果都不串会话。

不能以“页面做好了”“开关能保存”“状态文字能变化”代替真实功能闭环。
