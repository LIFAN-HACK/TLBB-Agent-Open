# 蓝钻 UU 32 位优先版产品重构开发文档

**交付对象：Claude Code**  
**授权方：蓝钻 UU 辅助工具开发组**  
**文档版本：v3.0**  
**核心原则：后端能力复用，前端 UI/UX 重构；32 位稳定版优先，64 位后续再做。**

---

## 1. 授权与工作边界

蓝钻 UU 辅助工具开发组授权 Claude Code 对开发组自有的蓝钻 UU 相关客户端、脚本、配置、数据文件、资源文件、题库、字库、OCR 模板、业务流程和历史模块进行分析、整理、解包、重构与迁移。

本次授权目录包括但不限于：

```text
<LEGACY_DATA_ROOT>
```

该目录下现阶段重点模块包括：

```text
uu
单师门普通版-1.37
队员马 - 双开版
授权答题
马2.31
跑商OL
生活王1.4.0
挖矿2.15
挖图-1.91
宾利帮贡五合一-sp.exe
```

Claude Code 可以对以上自有模块进行以下工作：

1. 静态分析程序结构、资源结构、配置结构和数据文件。
2. 解包或提取开发组自有模块中的可复用数据。
3. 整理旧客户端中的 OCR 字库、图片模板、坐标配置、流程配置、任务数据、题库数据和业务状态机。
4. 从不同开发人员编写的旧模块中比较实现质量，优先选用最稳定、最清晰、最可维护的实现。
5. 在新产品中复用旧模块的有效后端逻辑、配置、数据源和流程设计。
6. 移除开发组自有客户端内部旧的登录、注册、账号绑定、充值、改密、授权校验等入口和依赖。
7. 将旧功能整合到统一的新前端和统一后端执行框架中。

边界要求：

1. 本次移除登录认证仅限蓝钻开发组自有工具、自有模块、自有授权系统的旧登录认证，不包括第三方游戏、第三方平台、第三方安全组件或第三方账号体系。
2. 不得绕过、破坏、规避第三方游戏客户端、平台、验证码、反作弊或安全组件。
3. 如果某旧 EXE 只有二进制文件，没有源码，不要把“二进制补丁”作为主路线；应优先提取可授权复用的数据、配置、字库、资源和流程，然后在新后端中重写实现。
4. 所有从旧模块提取的数据和逻辑必须记录来源路径、用途、可信度和接入位置。

## 2. 项目背景

当前蓝钻 UU 原始客户端功能较多，但 UI 非常陈旧，界面信息密度高、控件混乱、配置分散、功能说明不清晰。原客户端主要由多个页签和大量文本框、按钮、复选框组成，包括：

```text
登录使用
注册账户
账户绑定
账户充值
账户改密
基本设置
按键打怪
挂机返点
副本设置
马贼设置
抢抢
自动反贼
盟会采集
自动和尚
```

从运行态调研看，`uu` 客户端是最重要的数据和逻辑来源。它的核心价值不在 UI，而在后端设计：

```text
32 位插件 / 运行库能力
固定字库识别能力
简单但稳定的状态机
按键打怪与技能节奏控制
窗口绑定和截图识别
马贼、反贼、和尚、三环等活动流程
```

已知运行态线索：

```text
UU 本体：32 位进程
核心释放文件：C:\sys\az.dll
核心释放文件：C:\sys\dz.dll
核心字库文件：C:\sys\aj.txt
主要游戏目标：32 位 Game.exe
64 位客户端后续再做，不作为第一阶段目标
```

`aj.txt` 很关键，它类似自建固定字库 / 模板 OCR 数据源，包含怪名、地图名、队伍提示、目标提示、系统提示、副本流程提示等识别词。新产品应借鉴这种“字库识别 + 状态机”的后端思路，而不是盲目堆内存读取或复杂 OCR。

## 3. 总体产品目标

本次项目目标是做一个新的蓝钻 UU 整合版客户端：

```text
后端：优先复用 uu 和 <LEGACY_DATA_ROOT> 中旧模块的成熟逻辑、数据和流程。
前端：完全重构，做现代化、清晰、模块化、可配置、可维护的新 UI/UX。
版本策略：先完成稳定可用的 32 位版本；32 位完成后，再规划 64 位版本。
```

产品定位：

1. 不是简单换皮。
2. 不是继续维护旧 UI。
3. 不是把多个旧客户端粗暴打包到一起。
4. 是将多个自有旧模块中的有效能力抽取出来，形成统一后端能力层，再由新前端统一管理。

核心原则：

1. `uu` 为第一优先数据源和逻辑来源。
2. 其他模块作为补充来源，用于补齐单师门、跑商、生活、挖矿、挖图、帮贡、答题、队员马等功能。
3. 优先选择旧模块中最稳定、最合理、最少副作用的实现。
4. 旧 UI 全部废弃，新 UI 重新设计。
5. 旧功能不是全部一次性照搬，优先落地最重要、最成熟、最能提升产品价值的功能。
6. 所有快捷键必须支持自定义录入和持久化保存。

## 4. 第一阶段产品策略：32 位优先

### 4.1 为什么先做 32 位

当前调研结论显示：

```text
uu 是 32 位程序。
核心插件 az.dll / dz.dll 是 32 位。
原始稳定流程主要围绕 32 位 Game.exe。
老式窗口钩子、截图、按键、插件调用和可能的内存读取都天然更适配 32 位客户端。
```

因此第一阶段不要在 64 位客户端上重复造轮子。先做 32 位版本，目标是：

1. 快速复用蓝钻原有稳定逻辑。
2. 快速完成新 UI 与后端能力整合。
3. 先把按键打怪、马贼、抢 NPC、反贼、和尚、三环等核心功能跑稳定。
4. 后续再以 32 位稳定框架为基础，独立规划 64 位数据读取和适配。

### 4.2 第一阶段不做的事情

第一阶段暂不做：

```text
64 位 Game.exe 的完整内存对象重找
64 位目标对象、技能栏对象、宠物对象深度读取
将 32 位 az.dll / dz.dll 强行改成 64 位
盟会采集正式执行逻辑
复杂插件化市场
全功能一次性重写
```

### 4.3 后续 64 位方向

32 位稳定版完成后，再启动 64 位专项：

1. 64 位窗口绑定和截图识别可以复用。
2. 字库识别和状态机可以复用。
3. 按键发送可以复用。
4. 内存读取、目标对象、技能栏、宠物对象需要独立做 64 位 profile。
5. 64 位不使用旧的 32 位插件链。

## 5. 旧客户端问题总结

从截图和运行态调研看，旧客户端主要问题如下：

1. 登录界面占据主入口，业务功能被旧授权体系强耦合。
2. UI 陈旧，缺少现代化布局。
3. Tab 过多但没有清晰信息架构。
4. 大量输入框无明确标签，用户不知道字段含义。
5. 多个模式之间配置割裂。
6. 配置保存、加载、恢复机制不清晰。
7. 日志和运行状态展示弱。
8. 按键配置不够友好。
9. 马贼、反贼、和尚、副本等状态机隐藏在旧程序内部，缺少可视化控制。
10. 多个旧客户端之间功能重复，需要整合优选。

新产品必须解决这些问题，而不是复制旧界面。

## 6. 新产品信息架构

新前端建议采用“左侧绑定与角色区 + 右侧功能工作区 + 底部日志状态区”的结构。

```text
┌──────────────────────────────┬─────────────────────────────────────────────┐
│ 左侧：窗口绑定 / 角色 / 配置   │ 右侧：功能 Tab                              │
│                              │                                             │
│ 拖拽绑定窗口                  │ Tab1 挂机                                   │
│ 绑定窗口卡片                  │ Tab2 活动                                   │
│ 角色头像 / 窗口信息            │ Tab3 生活 / 收益                             │
│ 32 位客户端检测状态            │ Tab4 任务自动化                              │
│ 当前配置方案                  │ Tab5 设置 / 数据源 / 调试，可选              │
│ 启动 / 暂停 / 停止             │                                             │
├──────────────────────────────┴─────────────────────────────────────────────┤
│ 底部：运行日志 / 识别结果 / 状态事件 / 错误信息                              │
└────────────────────────────────────────────────────────────────────────────┘
```

### 6.1 左侧窗口绑定区

要求：

1. 模仿 uu 的拖拽绑定方式，但 UI 做现代化优化。
2. 支持拖拽一个准星或图标到游戏窗口。
3. 绑定后展示：
   - 角色头像或角色区域截图
   - 窗口标题
   - 进程路径
   - PID
   - HWND
   - 客户端位数：32 位 / 64 位
   - 当前配置方案
   - 当前运行状态
4. 第一阶段只允许对 32 位 `Game.exe` 启动核心功能。
5. 如果绑定到 64 位客户端，UI 提示：

```text
当前为 64 位客户端。第一阶段仅支持窗口识别与基础按键测试，完整功能请使用 32 位客户端。
```

### 6.2 左侧账号与通用设置

登录认证移除后，不再显示旧的登录、注册、充值、绑定、改密 Tab。

保留的业务设置应改造成：

1. 当前角色配置。
2. 自动重连。
3. 自动上号，若旧模块中存在稳定逻辑，可作为后续功能接入。
4. 喊话配置。
5. 配置方案管理。
6. 日志和异常处理。

敏感信息不得明文保存。如果旧模块中存在账号密码保存逻辑，必须迁移为安全存储或移除。

## 7. 功能模块规划

## 7.1 Tab1：挂机

Tab1 是第一阶段最核心模块，优先级最高。

### 7.1.1 普通按键打怪

来源优先级：

```text
第一来源：uu
第二来源：其他挂机类模块
第三来源：现有项目中旧挂机逻辑
```

功能要求：

1. 自动打怪。
2. 技能快捷键自定义录入。
3. 技能释放间隔自定义。
4. 技能顺序可调整。
5. 公共 CD 保护。
6. 打怪状态识别。
7. 只打红怪 / 指定目标，按旧逻辑可用程度接入。
8. 打红名人，按旧逻辑可用程度接入。
9. 峨眉加血。
10. 打死换怪。
11. 怪物超时处理。
12. 无目标时重新选怪。
13. 目标距离过远时处理。

UI 要求：

1. 不能沿用旧的 `F1/F2/F3...` 一排小输入框。
2. 改为技能表格或卡片：

```text
技能名称 | 快捷键 | 间隔秒 | 启用 | 优先级 | 释放条件
```

3. 快捷键必须支持用户直接录入，例如：

```text
F1
F2
Alt+1
Ctrl+Q
Shift+F3
```

4. 支持录入检测，避免非法快捷键。
5. 支持一键恢复默认。
6. 支持保存为技能方案。

### 7.1.2 挂机返点

旧客户端中有“挂机返点”页签，包括坐标、死亡、土灵返点等逻辑。新 UI 需要改成清晰配置。

功能要求：

1. 挂机点保存。
2. 定点打怪返点。
3. 打怪土灵返点。
4. 死亡返点。
5. 死亡次数统计。
6. 死亡记录。
7. 卡点检测。
8. 定时返回。
9. 返回后继续打怪。

UI 要求：

```text
返点配置
- 当前坐标读取
- 添加返点
- 返点列表
- 返回方式：走路 / 土灵珠 / 其他旧逻辑
- 死亡后动作：停止 / 返点 / 重新挂机
```

### 7.1.3 BOSS / 马贼模式

马贼模式是 P0 核心功能，优先从 `uu` 提取。

已知旧模式特点：

```text
自动跟随队长
识别队长状态
识别马贼 / 马贼喽啰 / 夺宝马贼
只打指定马贼类型
打死后换目标
队员马、双开版可能包含更适合的跟随和队员逻辑
```

功能要求：

1. 马贼模式独立成 `HorseBanditModeController`，不要混在普通挂机大循环里。
2. 支持队长 / 队员角色选择。
3. 支持自动跟随队长。
4. 支持申请入队 / 同意申请 / 组队跟随等旧识别词迁移。
5. 支持只打：
   - 夺宝马贼
   - 马贼喽啰
   - 旧模块中已有的其他马贼目标
6. 支持红马 / 绿马策略，按旧数据实际能力接入。
7. 支持地图和坐标识别。
8. 支持打完后重新寻找目标。
9. 支持异常处理：
   - 找不到队长
   - 丢失跟随
   - 目标丢失
   - 战斗超时
   - 人物死亡
   - 无法选中目标

可复用来源：

```text
uu
马2.31
队员马 - 双开版
```

Claude Code 需要比较这三个来源，选择最合理的后端逻辑。原则：

1. `uu` 作为主流程来源。
2. `马2.31` 补充目标识别、马贼策略或坐标数据。
3. `队员马 - 双开版` 补充队员跟随、双开协同、组队状态逻辑。

### 7.1.4 副本模式

旧客户端有“副本设置”，包括：

```text
老三1 / 老三2 / 老三3
新三1 / 新三2 / 新三3
队伍编号
执行副本
结束清包
我去左桥
用于新三2 boss 不同站位
```

新 UI 需要整合为副本任务卡片。

功能要求：

1. 自动三环为第一优先副本。
2. 老三环和新三环分开配置。
3. 支持队伍编号。
4. 支持角色站位配置。
5. 支持执行次数。
6. 支持结束后清包。
7. 支持执行完成后继续挂机或停止。
8. 支持副本状态日志。

后续再扩展：

```text
反贼
宵小
宝宝丹
棋局
楼兰寻宝
其他旧模块已有副本
```

## 7.2 Tab2：活动

活动 Tab 用于集中管理抢 NPC、自动反贼、自动和尚等。

### 7.2.1 抢 NPC

旧客户端“抢抢”页签包含：

```text
抢反
抢上架
抢箱子
抢小(丹)
高甲卫
高甲223
抢小2
抢丹和尚
```

新 UI 需要重构为“目标类型 + 策略 + 执行动作”。

功能要求：

1. 抢反。
2. 抢小。
3. 抢和尚。
4. 抢箱子，按旧逻辑可用程度决定是否接入。
5. 抢上架，按旧逻辑可用程度决定是否接入。
6. 支持目标优先级。
7. 支持扫描间隔。
8. 支持点击 / 交互间隔。
9. 支持失败重试。
10. 支持日志记录每次发现、点击、失败、成功。

来源优先级：

```text
uu
授权数据目录中的其他抢 NPC / 活动模块
```

### 7.2.2 自动反贼

旧客户端有“自动反贼”页签。

功能要求：

1. 自动刷反。
2. 支持坐标组。
3. 支持保存设置。
4. 支持队长 / 队员逻辑。
5. 支持自动跟随。
6. 支持目标识别。
7. 支持开始、暂停、停止。
8. 支持异常恢复。
9. 支持副本 / 活动冲突提示。

用户已明确：自动刷反是重点功能，需要优先落地。

### 7.2.3 自动和尚

旧客户端有“自动和尚”页签，并备注与自动刷反时间冲突。

功能要求：

1. 自动和尚。
2. 支持雁南 / 西湖 / 洱海等旧界面已有地图选项，具体以旧数据为准。
3. 支持活动开始前后时间窗口。
4. 支持副本结束前 5 分钟退出或切换。
5. 支持与自动刷反的冲突管理。
6. 支持运行日志和错误恢复。

### 7.2.4 活动冲突管理

新 UI 需要增加活动冲突提示：

```text
自动刷反、自动和尚、副本执行、马贼模式不能同时抢占同一个窗口控制权。
```

需要设计 `ActivityScheduler`：

1. 同一窗口同一时间只能有一个主执行模式。
2. 可设置优先级。
3. 到时间自动切换。
4. 切换前执行安全收尾。

## 7.3 Tab3：生活 / 收益

生活类模块主要从以下来源整合：

```text
生活王1.4.0

挖图-1.91
```

注意：怀旧服原始服暂未开放盟会采集，因此“盟会采集”第一阶段不做正式执行逻辑，只保留前端占位或隐藏。

### 7.3.1 挖矿

4. 支持背包满处理。

### 7.3.2 挖图

功能要求：

1. 从 `挖图-1.91` 提取地图、坐标、流程配置。
2. 支持寻路、使用藏宝图、处理异常结果。
3. 支持收益日志。

### 7.3.3 材料加工

用户明确提到“材料加工”是重点补充功能。Claude Code 需要在授权数据目录中搜索是否存在相关实现或数据。

搜索关键词：

```text
材料
加工
生活
采集
制造
配方
合成
矿
药
种植
```

功能要求：

1. 提取材料加工配方或流程。
2. 支持批量加工。
3. 支持材料检查。

## 13. 技术方案建议

Claude Code 需要基于当前仓库实际情况最终决定技术栈，但第一阶段建议遵守以下约束：

1. 目标运行环境以 Windows 桌面为主。
2. 第一阶段优先支持 32 位游戏客户端。
3. 如果需要复用 32 位旧 DLL 或插件，执行层必须是 x86。
4. 新 UI 与自动化执行层必须解耦。
5. 即使 UI 是现代技术栈，核心执行也应通过 `AutomationWorker32` 或等价模块运行。

推荐两种路线：

### 路线 A：单体 32 位桌面客户端

适合快速落地。

```text
UI + Core + Worker 全部以 x86 发布
```

优点：

1. 兼容旧 32 位能力简单。
2. IPC 少。
3. 快速完成 MVP。

缺点：

1. 后续 64 位扩展不够优雅。
2. UI 进程和执行进程耦合较高。

### 路线 B：现代 UI + 32 位 Worker

推荐中长期路线。

```text
Modern UI Shell
  ↕ IPC / Command Bus
AutomationWorker32
  ↕ Legacy Adapter / OCR / Input / Capture
32 位 Game.exe
```

优点：

1. 前端现代化不受 32 位限制。
2. 旧后端能力隔离在 Worker 中。
3. 后续可新增 `AutomationWorker64`。
4. 更容易测试和维护。

缺点：

1. 初始工程量略高。
2. 需要设计 IPC 和事件总线。

建议 Claude Code 优先评估路线 B；如果当前开发进度要求极快，可以先用路线 A 做 MVP，但代码结构仍应按 Worker 边界设计，避免后续无法拆分。
