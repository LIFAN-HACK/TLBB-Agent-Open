# TLBB Agent 最终目标模式与落地任务清单

> 用途：作为 TLBB Agent 后续开发、验收、排期和对齐目标的统一文稿。  
> 核心结论：TLBB Agent 不是重新发明一套新辅助，也不是复刻旧 UI；它是把龙伴行 / 龙伴行自有授权数据中已经存在、可验证、可迁移的成熟功能，去掉登录链路授权链后，重新落到一个现代化、可维护、可诊断的 32 位稳定版客户端里。

## 1. 产品定位

产品名：TLBB Agent

第一阶段目标：32 位稳定版龙伴行功能整合客户端。

目标客户端：32 位 `Bin\Game.exe`。

暂缓目标：64 位 `Bin64\Game.exe`，不作为第一阶段阻塞项。

产品形态：Windows 桌面软件。

核心定位：
- 现代化前端。
- 迁移旧龙伴行 / 龙伴行授权数据中已有功能。
- 统一窗口绑定。
- 统一配置系统。
- 统一字库 / OCR / 模板识别。
- 统一输入服务。
- 统一状态机。
- 统一日志和诊断。

不是：
- 旧 UI 翻新。
- EXE patch 工具。
- 敏感链路运行器。
- 第三方平台、安全组件、验证码、风控或反作弊处理工具。
- 只做按钮和页面的演示壳。

## 2. 绝对边界

以下内容不进入 TLBB Agent 的运行链路：
- `敏感组件` 敏感链路。
- 登录链路窗口。
- 注册账户。
- 账户绑定。
- 账户充值。
- 账户改密。
- 会员账号验证。
- 会员密码验证。
- 旧远端授权请求。
- 授权失败弹窗。
- 账号过期提示。
- 启动强制登录拦截。

处理原则：
- 敏感链路相关内容只作为迁移时需要排除的对象，不作为依赖。
- 历史执行文件 / DLL 没有源码时，不声称“代码已经搬过来”；只迁移配置字段、字库、OCR 词、图色模板、坐标路线、流程参数、运行行为和状态机思路。
- 不修改 `本机授权数据目录` 原始文件。
- 不处理第三方游戏平台、第三方账号系统、第三方安全组件、反作弊、验证码或服务器风控。

## 3. 最终验收标准

最终我交付的不是文档，也不是截图，而是一个能启动、能绑定、能配置、能运行、能记录日志、能复测问题的 TLBB Agent 软件。

验收必须同时满足：
- 软件可以启动。
- 可以绑定 32 位 `Bin\Game.exe`。
- 绑定后显示窗口标题、PID、进程路径、32/64 位判断。
- 多开场景下，左侧绑定区域显示当前绑定角色的头像截图。
- 未绑定窗口时，启动按钮禁用。
- 绑定到 64 位客户端时提示当前阶段优先支持 32 位。
- 所有模式只能单选运行，同一时间一个窗口只跑一个主模式。
- 首页是通用配置，不是概览。
- 通用配置包含门派选择、技能预设、快捷键录入、目标选择预设、血蓝宠物阈值、公共 CD。
- 选择峨眉时，服务层自动启用加血相关能力，不能写死在 UI 事件里。
- 所有开关使用现代胶囊式点击切换。
- 功能区使用横向一级 Tab，Tab 内使用 tag / 分段选择切换具体模式，不使用卡片式功能菜单。
- 所有配置通过 `ProfileConfigService` 保存、加载、导入、导出。
- 所有日志通过 `RuntimeLogService` 输出。
- 所有窗口绑定、截图、OCR、按键、状态机逻辑都在服务层或控制器内，不能写在 WPF code-behind 或按钮事件里。
- 每个功能必须能看到来源、配置、运行状态、日志、失败原因和验收方式。
- 历史版本 / 龙伴行中已有的主要功能入口必须覆盖；没有真实可迁移证据的功能标记为“待确认”，不能假装已完成。

## 5. 后端架构目标

核心服务必须保留并真实承担职责：
- `AppInitService`：本地目录、配置目录、日志目录、导入数据导入目录、字库目录、插件目录初始化；不做远端登录认证。
- `WindowBindingService`：拖拽绑定窗口、获取 HWND/PID/标题/路径、判断 32/64 位、绑定状态维护。
- `WindowCaptureService`：窗口截图、客户区截图、指定区域截图、头像区域截图、OCR 输入图像生成。
- `TemplateOcrService`：接入历史版本 字库、解析 aj/zk/001 类模板字库、识别固定文字、怪名、NPC、地图、状态提示。
- `InputService`：按键发送、鼠标点击、PostMessage / SendInput 适配、快捷键、公共 CD、技能间隔。
- `StateMachineEngine`：统一状态机基础能力。
- `ProfileConfigService`：命名配置、保存、加载、导入、导出、版本迁移、备份、按角色/窗口/模式保存。
- `RuntimeLogService`：运行日志、错误日志、模块日志、状态机日志、复制、导出、过滤。
- `LegacyDataAdapter`：导入导入数据、转换统一格式、记录来源和迁移日志。

每个主模式必须是独立控制器或独立状态机：
- `NormalHangController`：普通挂机 / 按键打怪。
- `ReturnPointController`：挂机返点。
- `HorseBanditModeController`：马贼模式。
- `NpcGrabController`：抢 NPC。
- `AutoRebelController`：自动反贼。
- `AutoMonkController`：自动和尚。
- `DungeonController`：自动三环 / 副本。
- `TradeRunController`：跑商。
- `GatheringController`：采集。
- `MiningController`：挖矿。
- `TreasureMapController`：挖图。
- `TeacherTaskController`：单师门。
- `GuildContributionController`：帮贡。
- `QuizController`：答题题库。

强制规则：
- UI 只负责展示、输入、命令和状态绑定。
- code-behind 不写业务逻辑。
- 按钮事件不直接写窗口绑定、截图、OCR、按键、状态机、配置保存、导入数据导入。
- 不把 UI 控件状态当业务逻辑。
- 多个模式不混成一个大循环。

## 10. 功能覆盖矩阵要求

每个功能最终必须进入矩阵：

字段：
- 功能名称。
- 来源模块。
- 来源路径。
- 所属 Tab。
- 所属控制器。
- 配置是否完成。
- UI 是否完成。
- 识别是否完成。
- 输入是否完成。
- 状态机是否完成。
- 日志是否完成。
- 真实窗口是否验证。
- 当前状态：未接入 / 部分接入 / 已接入 / 运行中 / 错误 / 待确认。
- 遗留风险。

## 11. 我后续执行方式

我会按以下方式推进：

1. 先修正产品结构，不继续做卡片菜单。
2. 先稳定通用配置、绑定、头像截图、日志、配置保存。
3. 再做识别和输入底座。
4. 再按 P0 顺序逐个模式落地。
5. 每个模式完成后都补诊断命令、运行日志和验收记录。
6. 不把无源码历史执行文件 说成“代码已搬运”，只说“数据 / 流程 / 行为迁移并重写实现”。
7. 不引入 `敏感组件`。
8. 不为了快而把业务逻辑写进 UI。
9. 每完成一项，都更新功能覆盖矩阵。
10. 最终交付一个能运行的软件，而不是只交文档或界面。
