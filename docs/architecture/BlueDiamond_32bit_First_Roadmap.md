# 32 位优先路线图 (BlueDiamond_32bit_First_Roadmap)

> 架构阶段文档 · 明确第一阶段只做 32 位稳定版
> 生成日期：2026-06-20

---

## 1. 结论先行

第一阶段**只做 32 位稳定版**，目标客户端为 **32 位 `Bin\Game.exe`**。
64 位（`Bin64\Game.exe`）列为**二期独立专项**，第一阶段不为其造轮子、不阻塞 32 位交付。

此结论由本次静态扫描**实测支撑**（非假设）：

| 实测项 | 结果 |
|---|---|
| 历史版本.dvm.exe / vv.dvm.exe | **x86 (32 位)** |
| 全部模块主程序(8 个 csrss_*/shim/dysm/xxw10) | **x86** |
| 帮贡五合一.sp.exe | **x86** |
| 敏感组件 / 外部组件 | **x86** |

→ 龙伴行全部成熟资产都是 32 位链路。在 64 位上重做 = 抛弃现有稳定性。

---

## 2. 为什么 32 位更稳（基于资产观察）

产品文档判断已被扫描结果印证，历史版本 稳定性来自：

1. **32 位插件/运行库链**：`敏感组件`/`外部组件`/(历史版本 的 az.dll/dz.dll) 均为 32 位，与 32 位 `Game.exe` 同位运行，窗口钩子/注入/内存访问天然兼容。
2. **固定字库识别**：`aj.txt`/`zk.txt` 点阵模板 OCR，不依赖内存对象，**位数无关**且极稳定——这部分可直接服务 32 位且未来 64 位也能复用。
3. **简单状态机**：旧流程是有限状态机 + 截图识别 + 按键，副作用小、易恢复。

→ 第一阶段把 (2)(3) 做扎实，(1) 用托管代码在 x86 worker 重写。

---

## 3. 硬性约束

1. **不要把 32 位 DLL 硬转 64 位**。`敏感组件`/`外部组件`/`az.dll`/`dz.dll` 不做位数转换、不做 thunk hack。
2. **执行层必须是 x86**：任何需要与 32 位 `Game.exe` 同位的操作（注入/部分内存读取/同位 P/Invoke）跑在 **x86 worker 进程**。
3. **不复用旧内存地址**：config 中出现的 `地址1=266338304`、`句柄1/2` 等是运行态/版本相关值，**不固化**。
4. **64 位不阻塞 32 位**：凡"待 64 位"的能力，第一阶段在 UI 标注并禁用，不写半成品。

---

## 4. ClientAdapter 抽象（为二期预留，但一期只实现 32 位）

新架构提供 `IClientAdapter` 抽象，第一阶段**只实现 `Client32Adapter`**。

```
IClientAdapter
 ├─ DetectBitness(hwnd/pid) : x86 | x64 | unknown
 ├─ Capture(region)         : 截图（位数无关，可共用）
 ├─ SendInput(key/mouse)    : 按键/点击（位数无关，可共用）
 ├─ ReadState(...)          : 状态读取（32 位:字库识别为主；64 位:内存 reader，二期）
 └─ ...

 实现：
 ├─ Client32Adapter   ← 第一阶段唯一实现
 └─ Client64Adapter   ← 二期（占位接口，方法抛 NotSupported + UI 提示）
```

**位数无关、可被 64 位直接复用的能力**（一期就做对，二期免重写）：
- 窗口绑定 / 句柄 / PID / 标题 / 进程路径
- 截图（WindowCaptureService）
- 字库/模板识别（TemplateOcrService）
- 按键/鼠标（InputService）
- 状态机引擎、配置、日志

**位数相关、二期才做的能力**：
- 64 位内存 reader、指针链、对象结构（目标/技能栏/宠物对象）
- 任何依赖 32 位运行库注入的快捷读取

---

## 5. 绑定到 64 位窗口的处理

当用户拖拽绑定到 64 位 `Bin64\Game.exe`：
- WindowBindingService 正常识别并展示窗口信息（标题/PID/路径/位数）。
- 显示提示：
  > 当前为 64 位客户端。第一阶段仅支持窗口识别与基础按键测试，完整功能请使用 32 位客户端。
- 启动核心自动化按钮**禁用**（仅允许基础按键/截图测试）。

## 6. 第一阶段范围回执

| 范围 | 一期 | 二期 |
|---|---|---|
| 32 位 Game.exe 全功能 | ✅ | - |
| 64 位 Game.exe 窗口识别/基础按键 | 🔶 仅识别+测试 | ✅ 全功能 |
| 64 位内存对象重找 | ❌ | ✅ |
| 32 位 DLL 转 64 位 | ❌ 永不 | ❌ 永不(重写) |
| 字库识别/状态机/按键/截图/配置/日志 | ✅(位数无关) | 复用 |

## 7. 里程碑（32 位）

1. **M0 调研/架构**（本轮）：文档 + 技术栈决策。
2. **M1 骨架**：主窗口 + 左侧绑定 + 5 Tab 空壳 + 底部日志 + Profile + `Client32Adapter` 检测。
3. **M2 P0 核心**：窗口绑定→按键打怪→挂机返点→马贼模式→抢NPC→反贼→和尚→三环。
4. **M3 稳定化**：异常恢复、活动调度(ActivityScheduler)、配置迁移、日志过滤导出。
5. **M4 P1**：跑商/材料/挖矿/挖图/师门/帮贡/答题数据接入。
6. **二期立项**：64 位 Worker + reader（独立 roadmap）。

> 第一阶段不在 64 位内存重找或旧 UI 修补上分散精力。
