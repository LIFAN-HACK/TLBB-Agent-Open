# 龙伴行运行态目标模式

## 结论

运行态能力分两条线推进：

1. 主业务默认走外部安全链路：窗口绑定、截图、图色/OCR、后台按键、坐标/地图识别、用户采样资产。
2. 运行态研究只先做只读诊断：进程元信息、版本指纹、位数、窗口尺寸、后续可验证的快照接口。

当前阶段不做写内存、注入、Hook、补丁、绕过反作弊或在线对象表扫描。这个决定不是放弃能力，而是把容易导致封禁和不可控的问题隔离出主线。

## 目标模式

### 一期可交付目标

- 绑定 32 位 `Game.exe`。
- 生成只读进程证据：
  - PID
  - 窗口句柄
  - 标题
  - 进程路径
  - 32/64 位判断
  - 客户区尺寸
  - 主程序版本
  - 主程序 SHA256
  - 探针状态
- 定义统一运行快照模型：
  - 人物状态
  - 目标状态
  - 宠物状态
  - 场景状态
  - 背包状态
- 让业务控制器以后只依赖运行快照接口，不直接依赖某一种识别实现。

### 不在一期做

- 不对官方在线客户端做内存写入。
- 不注入 DLL。
- 不 Hook 游戏函数。
- 不枚举和扫描在线对象表。
- 不把不稳定地址写成配置项。
- 不把只读研究默认接入打怪、抢 NPC 或清包主流程。

## 数据来源优先级

1. 旧授权数据中的静态配置、字库、坐标、地图、流程数据。
2. 游戏窗口截图与用户标注采样。
3. 本地文件资产解析，例如 Lua、AXP、XML、INI、DAT、DB。
4. 只读进程元信息，用于版本和环境分流。
5. 只读运行态研究，必须单独开关、单独日志、单独证据输出。

## 运行快照抽象

后续控制器只认 `IRuntimeStateProvider`：

```text
NormalHangController
  -> IRuntimeStateProvider
      -> OcrRuntimeStateProvider
      -> StaticAssetRuntimeStateProvider
      -> ReadOnlyRuntimeStateProvider
```

这样打怪、回点、清包可以逐步替换底层识别方式，而不是把 OCR、图色、内存研究混进控制器。

## 验收标准

### P0

- 诊断工具可执行 `readonly-probe`。
- 找到正在运行的 32 位 `Game.exe` 后生成 JSON 证据。
- 证据中必须包含主程序 SHA256、版本、路径和客户区尺寸。
- 不发送按键、不点击、不出售、不读写游戏内存。

### P1

- 数据调试页可以显示运行快照来源和置信度。
- 外部截图链路和只读诊断链路都能输出同一套 `RuntimeSnapshot`。
- 当快照不可用时，业务逻辑必须降级到基础按键打怪，不阻塞。

### P2

- 基于用户采样资产优化玩家/怪物/BOSS/NPC 区分。
- 对抢小、抢反只使用可验证的外部识别或静态资产，不做高风险内存写入。

## 风险控制

- 任何运行态读取都必须可关闭。
- 任何读取失败都只能降级，不能卡死。
- 任何证据文件都要写明来源路径、窗口 PID、客户端版本。
- 不允许把研究代码直接变成默认业务路径。
